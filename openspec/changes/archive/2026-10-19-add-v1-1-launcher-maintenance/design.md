## Context

当前 CLI 将每个调用解析为 `Pin` 或 `Unpin` 加一个可选位置参数，并统一拒绝所有选项。应用层只支持按名称检查单个启动器；跨平台后端已经能够将单个入口解析为统一的受管元数据，但没有枚举能力。三个平台的入口格式和受管目录不同，因此 v1.1 既需要共享的状态判断与批处理编排，也需要各平台安全发现候选入口。

该变更跨越 CLI、应用编排、repository 发现和三个平台后端，设计产物用于固定共享边界与失败语义。行为要求见 repository-pinning delta spec。

## Goals / Non-Goals

**Goals:**

- 将帮助、单仓库 pin、list 与 prune 表示为互斥且类型化的 CLI 动作，避免在应用层重新解释原始参数。
- 复用一套平台无关的受管启动器有效性判断，使 list 与 prune 对同一入口得出相同结论。
- 让平台后端只负责安全枚举/解析受管入口和精确删除，应用层负责排序、检查、聚合结果与继续处理策略。
- 支持单项失败后继续扫描，并在保留完整诊断信息的同时返回整体失败。

**Non-Goals:**

- 不校验或修复 Visual Studio Code 安装，也不因 Code 缺失删除入口。
- 不自动修复内容损坏、路径变化或名称冲突的启动器；prune 只删除已确认对应无效 repository root 的受管入口。
- 不扫描既有平台受管目录之外的位置，不更改入口格式和目录布局。
- 不为 list 增加 JSON、过滤、静默等额外输出模式。

## Decisions

### 1. 将 CLI 解析结果改为动作枚举

`git-pin` 的解析结果表示为 `Pin(Option<OsString>)`、`Help`、`List` 或 `Prune`，`git-unpin` 保持独立的 `Unpin(Option<OsString>)`。帮助文本由 CLI 模块维护并作为成功结果输出；用法错误仍走现有错误通道。

这样可以在参数边界一次性保证模式互斥，并允许帮助在构造平台后端或访问文件系统之前返回。相比在现有 `Operation + argument` 上附加布尔标志，动作枚举不会产生不可表示或互相冲突的状态。

### 2. 为后端增加全量受管入口枚举

在 `LauncherBackend` 增加返回逐项结果的枚举接口。每个平台仅遍历自己的受管位置和命名模式，并使用与单项 `inspect` 相同的解析逻辑生成 `ManagedLauncher`。无法确认受管身份的普通外部入口直接忽略；符合 Git Pin 候选形式但元数据损坏的项作为带路径上下文的逐项错误返回。

逐项结果而不是“遇错即停”的整体 `Result<Vec<_>>`，可让应用层满足部分失败仍继续处理的要求。另一种方案是根据文件名构造名称再逐个调用 `inspect`，但这会重复目录过滤逻辑，且 macOS bundle 等候选到逻辑名称的映射更适合留在平台实现中。

### 3. 抽取不依赖 Code 的 repository root 自检

新增一个只检查记录路径的共享函数，结果类型包含 `Valid` 或带稳定原因分类的 `Invalid`。检查流程为：路径元数据确认存在且为目录；调用 Git 解析含工作树的顶层目录；按当前平台路径语义比较解析 root 与记录 root。Git 不可执行或检查期间发生无法分类的 I/O/进程错误视为检查失败，而不是自动判定僵尸；确定的“不存在、非目录、非工作树或 root 不匹配”才是可 prune 的无效状态。

复用现有 Git root 发现和路径比较规则，可避免 list/prune 与 pin 对规范路径的理解分叉。自检不调用 `vscode_executable`，明确隔离 IDE 可用性。

### 4. 使用“扫描记录 + 聚合错误”的批处理模型

共享扫描先收集每个候选的名称、root、路径和自检状态，并按平台的名称比较规则得到稳定排序；展示层使用统一文本格式输出。扫描同时保存枚举和检查错误。list 输出所有成功解析项后，如果错误集合非空则统一返回非零。

prune 消费同一扫描结果，只对 `Invalid` 项调用现有精确 remove，并继续处理后续项。成功删除立即生效并输出；枚举、检查或删除错误最终合并为带每项上下文的应用错误。此模型有意不做事务回滚，因为跨文件系统删除难以可靠回滚，而且规范要求保留已成功删除的结果。

### 5. 保持平台边界与安全删除约束

- Windows 只枚举 `.pinned_repo` 下符合受管 `.lnk` 规则且能读出 Git Pin 元数据的文件。
- Linux 只枚举 applications 目录下 `git-pin-*.desktop` 候选，并验证现有受管标记/字段后接受。
- macOS 只枚举 `$HOME/Applications/Git Pin` 下的 `.app` bundle，并验证现有 bundle 元数据后接受。

prune 始终使用枚举所得的完整 `ManagedLauncher` 调用精确删除，不根据用户可控名称拼接后直接删除。这样保留“只删已验证受管入口”的既有安全边界。

## Risks / Trade-offs

- **[Git 暂时不可执行会让本可判定的入口无法检查]** → 将其报告为操作错误而非僵尸，避免在环境故障时误删全部入口。
- **[repository 在扫描与删除之间恢复或变化]** → 删除前保留已扫描的受管身份，并可在应用层对待删项执行一次轻量复检；若状态已恢复则跳过删除。
- **[平台元数据解析逻辑在 inspect 与 list 间漂移]** → 每个平台抽取单一候选解析函数，由精确检查与枚举共同调用，并增加相同 fixture 的一致性测试。
- **[人类可读输出未来难以作为稳定机器接口]** → 本版本仅承诺确定排序和必要字段，不承诺 JSON schema；测试验证语义片段而非空白布局。
- **[损坏候选无法确认是否受管]** → 无明确受管证据的入口不删除；若命名符合候选但解析失败则报告错误，留给用户人工判断，优先防止误删。

## Migration Plan

1. 先扩展共享类型、后端 trait 与 fake backend，使现有单项 pin/unpin 行为继续通过。
2. 逐平台实现共享候选解析及枚举，使用隔离目录 fixture 验证只发现受管入口。
3. 接入自检、list 和 prune 编排，再更新 CLI 分派与用户文档。
4. 通过现有及新增的单元、跨进程和三平台 CI 测试后发布 v1.1；无需迁移已有启动器，它们继续使用原目录与格式。
5. 若需回滚，可恢复 v1.0 可执行文件；v1.1 未改变有效入口格式，已由 prune 删除的僵尸入口无需恢复，有效入口不受影响。
